Project Overview

What Is This Project?

The full arc — from the problem statement to the current working system.

Modern GPU clusters in HPC (High-Performance Computing) environments typically schedule jobs using FIFO (First-In, First-Out) — the simplest possible policy. A job joins the queue, waits its turn, and is dispatched when enough GPUs are free. This works, but it ignores everything the cluster knows: how fragmented the GPUs are, how many jobs are competing, how large those jobs are, and whether the cluster is trending toward idle or contented.

This project builds a proactive scheduler: one that uses a trained machine learning model to predict how long each queued job will actually wait, then reorders the queue so jobs that can be served quickly are served first. The entire system is built on a custom discrete-time cluster simulator written from scratch — no external HPC frameworks, just Python.

"The goal is not to break FIFO fairness — it is to make smarter decisions about which job to attempt next, using cluster state as a signal."

Phase 01 — Foundation

The GPU Cluster Simulator

Building the synthetic environment from scratch — the source of all training data.

Before any ML could be trained, the project needed a realistic source of labelled experience. Real HPC clusters are not accessible, so a custom discrete-time event simulator was built entirely in Python. Every timestep, the simulator processes job arrivals, releases completed jobs, updates cluster state, and attempts to schedule waiting jobs — exactly as a real scheduler would.

The cluster is modelled as 8 nodes each holding 4 GPUs (32 GPUs total). Jobs require between 1 and 8 GPUs and run for 5–20 timesteps. Allocation is greedy: GPUs are filled node-by-node until the job's demand is met. If the cluster cannot satisfy the job, the allocation is rolled back atomically.

minimal_gpu_cluster.py Python
Prototype / Proof-of-Concept
The very first simulator written for this project. Implements the Job, Cluster, and simulate() classes with a FIFO scheduler. No dataset generation — this was purely to validate that the simulation logic (allocation, release, queue management) worked correctly before scaling up. Tracks GPU utilisation and average wait time as sanity metrics.

Config: 8 nodes, 4 GPUs each, 50 jobs, SIM_TIME = 200.
dataset_minimal_gpu_cluster.py Python
First Dataset-Producing Simulation
Extended the minimal simulator to capture feature snapshots at every job's arrival moment — the cluster's state at the instant the job enters the queue. This is the key insight: the label (did the job wait ≤ DELTA_T timesteps?) can only be determined after the simulation, but the features must be recorded at arrival.

Produced dataset.csv with 110 samples (one run). Label: binary feasibility — 1 if wait ≤ 3 timesteps, 0 otherwise.
dataset_minimal_gpu_cluster.py — feature snapshot logic Python 
# Captured at job arrival — before it enters the queue
for job in jobs:
    if job.arrival_time == t:
        job.feature_snapshot = {
            "job_gpu":       job.num_gpus,
            "total_free":    cluster.total_free_gpus(),
            "queue_length":  len(queue),
            "running_jobs":  len(running_jobs),
            "max_free_node": max(cluster.nodes),
            "variance_free": np.var(cluster.nodes),
        }
        queue.append(job)  # THEN it joins the queue

# Label assigned after simulation, linked via job reference
wait_time = job.start_time - job.arrival_time
label = 1 if wait_time <= DELTA_T else 0

Phase 02 — Data Engineering

Dataset Generation & Feature Engineering

Scaling to 2,200 samples with richer features and a regression target.

110 samples from a single simulation run are not enough to train a robust model. Worse, a single run captures only one load profile. The solution: run the simulation 20 times independently with different random job arrivals, collecting all samples into a single pooled dataset — 2,200 rows, far more diverse.

At the same time, the feature set was expanded beyond the original 6 features. Two new signals were added: smaller_jobs_in_queue (how many queued jobs need ≤ the current job's GPUs) and demand_ratio (job demand vs. free GPUs). Critically, the target was changed from binary classification to continuous wait-time regression — a richer signal for the scheduler.

generate_large_dataset.py Python
Multi-Run Dataset Generator
Runs the full FIFO simulation 20 times, each with freshly randomised jobs. After each run it collects all completed jobs' feature snapshots and their actual wait times. Results from all runs are pooled into a single dataframe and saved as wait_dataset.csv. This is the primary training data source for the wait-time regression model.

Also captures two new features: smaller_jobs_in_queue and demand_ratio = job.num_gpus / (total_free + 1).
large_dataset.csv CSV
Classifier Training Data — 2,200 rows
Produced by running the large dataset generator with a binary label column (feasibility within DELTA_T). Used to train the initial classifier models (Logistic Regression, Random Forest, XGBoost Classifier) before the project pivoted to regression. Contains the same 6 + 2 = 8 features as wait_dataset.csv but with a binary label instead of continuous wait time.
wait_dataset.csv CSV
Regression Training Data — 2,200 rows, 9 columns
The primary dataset for the regression model. Same 8 features as large_dataset.csv but with wait_time (integer, timesteps) as the target column instead of a binary label. Wait time ranges 0–75 timesteps with mean ~17.8, giving the model a wide spread to learn from. Columns: job_gpu, total_free, queue_length, running_jobs, max_free_node, variance_free, smaller_jobs_in_queue, demand_ratio, wait_time.

Phase 04 — Regression Model

Wait-Time Regression

From binary classification to continuous prediction — the model that actually drives the scheduler.

A binary label tells the scheduler "this job will start soon" or "it won't" — but it can't rank two jobs that are both predicted to start soon. A continuous wait-time prediction gives a score per job that can be sorted directly. This is the architectural pivot that made the proactive scheduler possible.

train_wait_model.py Python
XGBoost Regressor — Original Wait Model
Trains an XGBRegressor (200 estimators, lr=0.05) on wait_dataset.csv. Evaluates with MAE and R² score. Saves the model as wait_model.pkl for use in the scheduler. Also generates feature_importance.png — which revealed the critical problem: smaller_jobs_in_queue had ~82% feature importance, essentially encoding the job's queue position directly.

Results: MAE ≈ 5.25 timesteps, R² = 0.833.
wait_model.pkl Pickle
Serialised Model — Original (with leaky feature)
The trained XGBoost Regressor serialised with Python's pickle. Loaded at runtime by the proactive scheduler. This is the original model, trained with the leaky smaller_jobs_in_queue feature. Superseded by wait_model_v2.pkl after the feature fix in Phase 06.
feature_importance.png Image
Feature Importance Plot — Led to the Phase 06 Discovery
Bar chart of XGBoost feature importances for the original model. This plot was the diagnostic breakthrough: smaller_jobs_in_queue dominated at 82% importance. In a FIFO scheduler, the number of smaller jobs in front of you is almost equivalent to your queue rank — giving the model a near-direct leak of the scheduling order into the features. High accuracy, but not from genuine cluster-state reasoning.

Phase 05 — Scheduler Implementation

The Proactive Scheduler

Replacing FIFO with ML-guided queue prioritisation and benchmarking against the baseline.

Two proactive scheduler implementations were built. The first (proactive_scheduler.py) trained the XGBoost Classifier inline and used its feasibility probability to sort the queue — jobs predicted as most likely to start soon go first. The second (proactive_Schedule_v2.py) loads the pre-trained wait-time regressor from disk and sorts by predicted wait time ascending (lowest expected wait → serve first).

Both are benchmarked over 10 independent runs against the FIFO baseline, using the same randomly generated job sets for a fair comparison.

proactive_scheduler.py Python
Classifier-Based Proactive Scheduler v1
Trains an XGBoost Classifier on large_dataset.csv inline, then uses it to score jobs in the queue by feasibility probability (predict_proba). At each timestep: score every queued job, sort descending by probability, dispatch the highest-probability job that can currently fit. Breaks FIFO order intentionally to serve more schedulable jobs.

Key design: Only dispatches one job per timestep (to avoid starvation), but re-scores the full queue every tick.
proactive_Schedule_v2.py Python
Regression-Based Proactive Scheduler v2
Loads the pre-trained wait_model.pkl from disk. Uses model.predict() (continuous wait time) instead of predict_proba() to rank jobs. Sorts the queue ascending by predicted wait time — jobs expected to wait the least go first. Also uses the richer 8-feature set including smaller_jobs_in_queue and demand_ratio.

Benchmark: 10-run comparison vs FIFO baseline, reporting average wait time and GPU utilisation.
proactive_Schedule_v2.py — core scheduling loop Python 
if queue:
    # Score every queued job with the regression model
    scored = []
    for job in queue:
        features = get_features(job, cluster, queue, running_jobs)
        predicted_wait = model.predict([features])[0]
        scored.append((predicted_wait, job))

    # Sort ascending — lowest predicted wait first
    scored.sort(key=lambda x: x[0])
    queue = [job for _, job in scored]

# Dispatch the first fitting job (break after one to avoid starvation)
for job in queue[:]:
    if cluster.total_free_gpus() >= job.num_gpus:
        if cluster.allocate(job, t):
            running_jobs.append(job)
            queue.remove(job)
            break  # ← one job per tick

Phase 06 — Active

Feature Leakage Fix & Model v2

Discovering a near-leakage problem and rebuilding with principled cluster-state features.

The feature importance plot from Phase 04 raised a red flag. smaller_jobs_in_queue held 82% of the model's importance. In a FIFO scheduler, the number of jobs in queue with fewer GPU requirements than yours is almost identical to your rank in the queue. The model was essentially memorising queue position → wait time, not learning genuine cluster dynamics. This is near data leakage.

Data Leakage Warning

Why is this a problem? The proactive scheduler reorders the queue — so at inference time, a job's smaller_jobs_in_queue value was computed under FIFO ordering but the queue is no longer FIFO. The feature becomes meaningless (or worse, misleading) once the scheduler starts reordering. A model that learned from a feature that doesn't exist at inference time will give systematically wrong predictions.
