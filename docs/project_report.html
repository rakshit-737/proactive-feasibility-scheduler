Project Overview

The Full Research Arc

From problem statement to 30-phase research pipeline with audited, regenerated results.

Modern GPU clusters in HPC (High-Performance Computing) environments typically schedule jobs using FIFO (First-In, First-Out) — the simplest possible policy. A job joins the queue, waits its turn, and is dispatched when enough GPUs are free. This works, but it ignores everything the cluster knows: fragmentation, competing jobs, job sizes, and whether the cluster is trending toward idle or contention.

This project builds a proactive scheduler: one that uses a trained machine learning model to predict how long each queued job will actually wait, then reorders the queue so jobs that can be served quickly are served first. The entire system is built on a custom discrete-time cluster simulator written from scratch — no external HPC frameworks, just Python. The research spans 30 phases: from simulation and dataset generation through feature engineering, multi-model comparison, fairness analysis, SHAP explainability, scaling and saturation studies, online learning, concept drift, ROI analysis, and reproducibility. All 30 phases are now complete: the v3.2 research extensions closed Phase 25 by validating against two real Parallel Workloads Archive traces (LANL CM-5 and SDSC SP2), and added backfill baselines, a bounded-fairness wait-budget sweep, and uncertainty-aware scheduling.

"The goal is not to break fairness — it is to make smarter decisions about which job to attempt next, using cluster state as a signal."

All three share the same 12-feature cluster-state schema, ensuring consistency and avoiding data leakage.

Phases 22–30: Hardening & audit (extended OOD study, saturation stress, deployment docs). All green. Phase 25 — real-trace validation — was closed by the v3.2 extensions: two real Parallel Workloads Archive traces (LANL CM-5 and SDSC SP2) were downloaded and evaluated; see the v3.2 chapter below.

Phase 04 Challenge: Feature Leakage

Initial regression (Phase 04) revealed a critical issue: the feature smaller_jobs_in_queue dominated feature importance (82%), essentially encoding FIFO queue rank. At inference time, the queue is reordered, making this feature meaningless or actively misleading. Phase 05 Fix: Replaced leaky features with 6 principled cluster-state signals valid at any scheduling policy. Result: the model now learns genuine cluster dynamics rather than queue position, and no single feature dominates importance. On a proper 20% holdout the clean model scores R² 0.837 / MAE 4.69 ts. A second honesty fix followed in the July 2026 audit: the evaluation script split the data after fitting, so the impressive R² it printed was in-sample; that figure was retired as dishonest and only holdout numbers are reported here.

Core Phases (01–05)

Phase 01: Cluster Simulation. Discrete-time event simulator modelling 8-node, 32-GPU heterogeneous cluster with FIFO baseline, greedy GPU allocation, and full state tracking.
Phase 02: Dataset Generation. 20 seeded runs × 110 jobs → 2,200 training samples (mean wait 16.41 ts, max 73), fully deterministic (seed 42, per-run 42+i). Feature snapshots captured at job arrival.
Phase 03: Classifier Comparison. Logistic Regression, Random Forest, XGBoost on binary feasibility (XGBoost strongest).
Phase 04: Wait-Time Regression. Extended to continuous regression — and exposed the feature-leakage issue described above.
Phase 05: Proactive Scheduler Benchmark. Fixed feature leakage, retrained model v2 (12 principled features, holdout R² 0.837 / MAE 4.69 ts). Scheduler loads v2 model and reorders queue; the definitive 40-run benchmark (Phase 08) measures a 7.71% mean-wait reduction.

Analysis Phases (06–09)

Phase 06: Multi-Model Regression. Benchmarked 7 algorithms on improved_wait_dataset.csv (holdout MAE/R²): LightGBM 4.61/0.848 · CatBoost 4.62/0.845 · XGBoost 4.69/0.837 · Random Forest 4.70/0.837 · MLP 4.71/0.840 · GradientBoosting 4.72/0.839 · LinearRegression 6.32/0.761. Exported thesis Table 1 metrics.
Phase 07: Load-Profile Expansion. Generated low/high/bursty datasets and evaluated XGBoost on each profile separately (MAE/R²): low-contention 0.20/0.80 · high-contention 13.08/0.91 · mixed-bursty 1.28/0.67.
Phase 08: 40-Run Statistical Benchmark. Paired benchmark on 40 seeds: FIFO 18.27 → proactive 16.70 ts mean wait, a 7.71% ± 8.87 improvement; paired t-test p = 1.4e-06, Wilcoxon p = 7.1e-06, bootstrap 95% CI [4.95%, 10.34%]; 33/40 runs positive.
Phase 09: Hyperparameter Tuning. Grid search over XGBoost configurations. Best tuned model: MAE 4.57 / R² 0.850 versus the default 4.69 / 0.837 — a modest but real gain.

Robustness & Explainability Phases (10–13)

Phase 10: Sensitivity Analysis (OOD). Measured model robustness under node-count shifts, runtime distributions, and arrival patterns — 72 shifted scenarios with the real model on real shifted simulations. Mean R² −0.31 (range −2.32 to +0.85); scheduling improvement ranges from −14% to +50%; mean failure rate ≈ 32%. Conclusion: retrain per regime and keep a FIFO fallback.
Phase 11: Ablation Study. Systematic 12-feature ablation with R² drop ranking. Dominant feature: job_gpu (R² drop 0.201), followed by queue_pressure (0.027) and queue_length (0.021); all other features contribute ≤ 0.005 each.
Phase 12: Fairness & Starvation Analysis. Fairness metrics (max wait, Gini, starvation count) across FIFO, proactive, and proactive+anti-starvation over 20 runs. Key honest finding: plain proactive reordering worsens tail latency (max wait 57.9 → 124.8 ts) and Gini (0.526 → 0.796) versus FIFO — the mean-wait gain (18.58 → 16.54 ts) comes at a fairness cost. The anti-starvation variant claws back tail latency (max 87.2, Gini 0.688) but bumps more jobs (starved count 30.2 vs 18.2). SLA compliance: 0.933 (FIFO) / 0.945 (proactive) / 0.863 (anti-starvation); run-level Jain index 0.918 vs 0.922.
Phase 13: SHAP Explainability. Generated summary, dependence, and force plots explaining model decisions. Validated feature interpretability.

Advanced Analysis Phases (14–21)

Phase 14: Trace Transfer (Synthetic Proxy). The LANL-style trace on disk is a synthetic proxy (labelled synthetic_proxy_trace) — an earlier version of this report mislabelled it as a real trace. The synthetic-trained model does not transfer even to the proxy: R² ≈ 0.015 / MAE ≈ 15 ts. Validation against genuine production traces (Phase 25) was completed in v3.2 and confirms the pattern: zero-shot transfer ≈ 0 on real data, while retraining on real cluster-state features recovers strong signal on a batch machine (see the v3.2 chapter).
Phase 15: Scaling Study. Evaluated cluster sizes from 8 to 256 GPUs. The proactive advantage shrinks as contention disappears: +14.4% at 8 GPUs, +5.1% at 32, and 0% at 128/256 GPUs — with no queue contention there is nothing to reorder.
Phase 16: Online Learning. Incremental model updates on a drifted stream using mini-batch retraining: MAE 6.98 → 6.88.
Phase 17: Concept Drift Detection. Rolling-MAE trigger for adaptive retraining: 7 triggers over an 880-sample stream.
Phase 18: ROI Analysis. Illustrative, assumption-heavy cost model: ≈ $78k/yr projected savings and 86% first-year ROI. Treat as a what-if scenario, not a measured outcome.
Phase 19: Reproducibility Kit. One-command pipeline (run_all_experiments.sh), Docker container, requirements.txt (re-pinned for Python 3.14 in the audit), comprehensive README.
Phase 20: Interactive Dashboard. dashboard.py provides real-time visualisation of scheduler decisions and performance metrics.
Phase 21: Publication Pipeline. Integrated tables, plots, and results into project_report.html and research_progress.html. GitHub Pages docs/ with interactive explorer (see docs/index.html).

Hardening & Audit Phases (22–30)

Phases 22–24: Extended Benchmarks. 5-scheduler benchmark over 20 runs (mean wait / max wait / Gini): SJF 12.00/143.5/0.782 · NN 15.69/134.2/0.796 · PROACTIVE 15.71/125.7/0.790 · PRIORITY 16.34/127.7/0.739 · FIFO 16.65/53.9/0.518. Throughput and utilisation are identical across all five — the policies trade mean wait against tail latency and fairness. All green. Phase 25: Real-Trace Validation — COMPLETE (v3.2). Two real Parallel Workloads Archive traces (LANL CM-5 1994–96 and SDSC SP2 1998) were downloaded, replayed chronologically, and evaluated. Zero-shot transfer of the synthetic-trained model fails on both (R² ≈ 0); a model retrained on honestly-derived real cluster-state features reaches R²(log) 0.494 on SDSC SP2 but only 0.101 on the weak-signal LANL CM-5. Full detail in the v3.2 chapter.
Phase 26: Saturation Stress. Under saturating load, utilisation exceeds 99.7% at 32–256 GPUs; batched inference costs 10–48 ms and total scheduling overhead stays below 5%.
Phases 27–30: Audit & Deployment. The July 2026 audit fixed 37 verified defects — including fabricated results in 4 phase scripts, the in-sample evaluation bug, and the fake real-trace label. Feature Set Rationale

Each feature is computed from observable cluster state at job arrival time and remains valid regardless of scheduling policy. Features span four categories: (1) Job demand: job_gpu and related sizing signals. (2) Queue dynamics: queue_length, queue_pressure. (3) Allocation feasibility: can_fit_now, fit ratios. (4) Cluster availability: node_availability, fragmentation and other derived metrics. Importance is spread sensibly — job_gpu leads at 26.1%, with queue_length (22.3%), node_availability (16.9%) and can_fit_now (12.2%) behind it and every remaining feature at ≤ 4.7% — nothing like the 82% domination of the retired leaky feature. The ablation study agrees: removing job_gpu costs 0.201 R², queue_pressure 0.027, queue_length 0.021, and every other feature ≤ 0.005.

v3.2 Research Extensions

Four new studies close out the research programme: reservation-based backfill baselines, a tunable bounded-fairness wait budget, uncertainty-aware dispatch with quantile models, and — closing Phase 25 — validation on two real supercomputer traces. All numbers regenerated; the negatives are reported as plainly as the wins.

4.1 Seven-Scheduler Benchmark (Out-of-Training Seeds)

The scheduler benchmark was extended from five to seven policies by adding EASY backfill and a predicted-wait hybrid (04_scheduler/backfill_scheduler.py), and re-run as 20 paired runs on out-of-training seeds (1000+i). PROACTIVE beats FIFO by 6.5% on these fresh seeds, versus 7.7% on the near-training benchmark — good generalization. Utilisation (0.637) and throughput are identical across all seven policies.

Semantics — Read Before Comparing

The benchmark's "FIFO" dispatches every fitting job each tick, i.e. it is already an unrestricted, no-reservation backfilling policy. EASY backfill adds a hard reservation for the head job (the head job is never delayed; runtime estimates are perfect, making it a strongest-case baseline). That reservation costs ≈45% mean wait — but delivers the best fairness in the whole study (Gini 0.365, max wait ≈55 ts). The hybrid PROACTIVE_BF (predicted-wait backfill ordering) ties EASY — an honest null result: model-guided ordering adds nothing once a head-job reservation constrains the queue.

4.2 Bounded Fairness: The Wait-Budget Sweep

Phase 12 showed that pure proactive reordering buys mean wait at the cost of tail latency. The v3.2 sweep (04_scheduler/fairness_budget_sweep.py, 20 paired runs, seeds 5000+i) makes that trade-off tunable: a job whose wait exceeds budget B timesteps is escalated to the front of the queue. The result is a smooth Pareto frontier between FIFO (reference mean wait 22.4 ts) and pure proactive (+13.2% mean-wait gain, max wait 136 ts).

The Operating Point

B = 60 keeps over half the unbounded mean-wait gain (+7.1% of +13.2%) while capping max wait at 81 ts instead of 136. Fairness becomes a dial, not a casualty.

Honest Negative — Tiny Budgets

Budgets of 0–30 ts are slightly worse than FIFO (−0.1% to −1.7%): constant escalation churn without enough freedom for the model to reorder productively. A wait budget only pays for itself once it is loose enough to let the predictor work.

4.3 Uncertainty-Aware Scheduling (Quantile Models)

A quantile XGBoost model (q10/q50/q90, 03_models/train_quantile_model.py) was trained to test two ideas: scheduling on a pessimistic q90 estimate (UCB) and using interval spread as an out-of-distribution alarm that triggers a FIFO fallback (GUARDED, spread trigger τ = p95 of in-distribution relative spread). Holdout quality: q50 MAE 4.61 vs 4.69 for the point model; the [q10, q90] interval achieves 68% empirical coverage against 80% nominal — under-dispersed, reported honestly. Benchmarks: 10 paired runs per scenario, seeds 7000+i.

Honest Negative Result

In the light-load small-cluster regime, every smart policy is worse than FIFO (−4.3% to −5.0%) and the spread guard fails to notice: it fires on just 0.2% of ticks because the under-dispersed intervals (68% coverage vs 80% nominal) stay narrow out of distribution. Interval width is not a reliable OOD alarm here. The drift-triggered FIFO fallback (rolling-MAE trigger from the concept-drift work) remains the deployment mechanism of record.

4.4 Real-Trace Validation — Phase 25 Closed

The project's longest-standing caveat is resolved. Two real Parallel Workloads Archive traces — LANL CM-5 (1024 processors, 1994–96, 122,055 usable jobs) and SDSC SP2 (128 nodes, 1998, 42,117 evaluated arrivals) — were committed to 02_data/ and evaluated (build_real_trace_datasets.py, real_trace_validation.py). Method: chronological replay of each recorded schedule reconstructs 8 honestly-derivable cluster-state features at every arrival. Transfer tests the synthetic-trained model via a rescaled 12-feature mapping with best-case affine calibration; retrain fits fresh on real features with a chronological 80/20 split, target log1p(wait minutes).

Honest Partial Negative — LANL

LANL CM-5 is a weak-signal machine: median wait ≈4 seconds, largely interactive traffic. Retraining lifts R²(log) only to 0.101 (MAE 33.7 min vs the median baseline's 33.5). Signal strength is machine-dependent: where queueing is thin, cluster-state features have little to explain.

The Strong Result — SDSC

SDSC SP2 is a heavy-tailed batch queue (p90 wait ≈15 h). The retrained model reaches R²(log) 0.494, MAE 622 min against a median baseline of R² −0.694 / MAE 684 min and a rolling-mean baseline of R² 0.016 / MAE 1009 min: cluster-state features explain roughly half the log-wait variance on a real batch supercomputer once retrained. Zero-shot sim-to-real transfer is ≈0 on both traces — now quantified on real data rather than assumed.

"Retrain per deployment" is no longer a caveat — it is an evidence-backed finding: zero-shot transfer fails on real traces, and retraining recovers strong signal wherever queueing dominates.
