## v3.4 headline: the ranking degeneracy

**The claim.** At any dispatch instant, every queued job observes the same cluster.
So in the feature vector only the job's own attributes can differ between two
co-queued jobs — and in this feature set every one of those is a deterministic
function of the requested size `g` given the state `S`:
`can_fit_now = 1[free(S) >= g]`, `gpu_fit_ratio = min(free(S)/g, 1)`,
`node_availability = |{n : free_n(S) >= g}|/N`, `queue_pressure = (Σ_Q − g)/(free(S)+1)`.
Therefore the learned score is `ŵ(j | S) = g_S(size_j)` and the induced order is
just the order of `g_S` over the queue's sizes. **The remaining seven features
describe only the cluster, so they shift every score by the same amount and cannot
reorder anything.** (`queue_pressure` does vary between co-queued jobs, but only
because it subtracts the job's own size — it is itself a deterministic function of
size given the state, so it cannot break the degeneracy.) The model, used as a
ranking function, is a per-instant lookup table from requested size to priority.
This argument is now written down formally as **Proposition 1** in `METHODOLOGY.md`
(with three corollaries, and its converse as Proposition 2). Two precisions come out
of writing it down. (i) The induced order is a *function* of size; it is **not**
necessarily the ascending-size order — the recovered size→priority table is monotone
in only 63.1% / 57.1% / 56.9% of instants (table below), so any phrasing like
"a permutation of the size order" overstates it. (ii) The premise is that the cluster
state is *shared*, which holds when the score is computed **at the dispatch
instant**; the Phase D attack section below shows what happens when it is not.

**The measurement** (`05_results/degeneracy/`, `04_scheduler/ranking_degeneracy.py`),
instrumenting dispatch decisions in three settings:

| | Synthetic | SDSC SP2 | LANL CM-5 |
|---|---|---|---|
| Ranking instants (≥2 queued) | 3,646 | 11,843 | 29,943 |
| Features total | 12 | 8 | 8 |
| Features varying across queue (mean) | 2.62 | 2.87 | 2.69 |
| **Equal size → different score** | **0** | **0** | **0** |
| Distinct scores per queue | 2.81 | 3.09 | 2.28 |

Zero counterexamples in 45,432 instants (41,786 from the two real traces plus
3,646 synthetic). The 7 synthetic cluster-state features
(and 4 of 8 on the traces) vary across the queue in **0.0%** of instants; every
feature that does vary (`job_gpu`/`job_procs`, `can_fit_now`, `gpu_fit_ratio`,
`node_availability`, `queue_pressure`) is a deterministic function of the
requested size. A ~9-job queue is partitioned into only 2.3–3.1 priority classes;
the learned order coincides with plain arrival order in **18–27%** of instants,
and — a separate, smaller count over the same instants, not a subset of that
figure — every queued job receives an *identical* score in **14–21%**. In the
latter the policy silently reduces to FCFS outright.

**Correction (v3.6).** An earlier draft of this paragraph read the 18–27% figure
*as* the all-tied fraction. That was a conflation and is retracted: 18–27% is
`pct_order_identical_to_arrival`, the fraction where the induced order equals
arrival order. All-tied implies arrival order, but not the converse, so that column
only *upper-bounds* the all-ties claim. The stronger property is now measured
directly in `pct_all_scores_tied` (17.1% / 14.4% / 20.7%, new column in
`ranking_degeneracy.csv`). Both facts support the degeneracy argument; only the
conflation was wrong, and both are stated above.

**The consequence — equivalence, tested properly** (paired TOST, margin 10% of
reference; `multi_scheduler_equivalence.csv`, `trace_scheduler_equivalence.csv`):

| Substrate | Metric | Δ (size sort vs ML) | p_TOST | Verdict |
|---|---|---|---|---|
| Synthetic | mean wait | +0.80% | 2.6e-16 | **equivalent** |
| Synthetic | bounded slowdown | +0.69% | 3.8e-18 | **equivalent** |
| SDSC SP2 | mean wait | −0.05% | 1.8e-12 | **equivalent** |
| SDSC SP2 | bounded slowdown | +2.7% | 7.4e-04 | **equivalent** |
| LANL CM-5 | mean wait | +14.4% | 0.77 | **inconclusive** |
| LANL CM-5 | bounded slowdown | +7.3% | 0.30 | **inconclusive** |

The two LANL verdicts previously read "not equivalent"; **that wording is retracted** — a
failed equivalence test is not a difference finding, and the power analysis below shows
those two tests could not have returned anything else.

On the synthetic benchmark the difference is +0.127 ts with 90% CI [+0.025, +0.228]
against a ±1.59 ts margin — the whole interval is inside the margin, so this is a
positive equivalence finding, not an underpowered null. The **MLP baseline is
bit-identical to the size sort on every metric of all 20 runs**: two model classes
over the same features collapse to the same one-line sort.

**On LANL the honest verdict is *inconclusive*, not "different".** The size sort is
14.4% worse on mean wait, but that difference does not survive Holm correction on the
paired t-test (p = 0.25; the Wilcoxon test disagrees at p = 0.015), it shrinks to
+7.3% at p = 0.60 on bounded slowdown, and TOST cannot certify equivalence either
(p = 0.77). With 20 windows LANL is neither shown equivalent nor shown different.

**And the LANL row cannot be settled on that trace at all (v3.6).** A Monte-Carlo power
analysis of the same paired test — 20,000 replicates, seed 31337 (outside every protected
seed family), margin 0.10 × the reference mean exactly as `simstats.tost_equivalence`
computes it — puts the achieved power of the LANL mean-wait equivalence test at **0.47%**
(0.00465; a bootstrap variant of the same calculation gives 5.8%). `tost_power.csv`,
`04_scheduler/tost_power.py`. A test with a 0.47% chance of certifying equivalence
returning "not equivalent" is not evidence of anything; that is stronger than calling the
row underpowered, and it is why the table above now reads *inconclusive*. Nor would more
windows fix it: the observed paired difference is 320.02 s against a 222.93 s margin, so
the effect lies **outside** the margin and *no* sample size can certify equivalence there
at 10% — the honest sentence is not "more windows would settle it". Establishing a
*difference* instead would need 29 windows, or 50 after Holm correction over the family of
11 tests, and LANL supplies only **28** disjoint 7-day windows. The bounded-slowdown row
is in the same position for the opposite reason: achieved power 7.97%, and certifying
equivalence there would need 440 windows against the 28 available. **The equivalence claim
rests on SDSC, and there it rests solidly**: the same analysis gives achieved power 1.000
on mean wait, where 3 windows would have sufficed and 29 are available (11 windows and
power 0.973 on bounded slowdown). Two limits belong with this: power computed from an
observed effect is post-hoc and is an estimate, not a design guarantee; and the supply of
disjoint windows is a property of the trace, not a budget we can raise.

An earlier draft of this section attributed the LANL result to its learned size table
being less monotone. **That explanation is wrong and is retracted**: the per-instant
monotone fraction is 57.1% on SDSC — where equivalence *does* hold — against 56.9% on
LANL, statistically indistinguishable, so monotonicity does not track where the
equivalence fires. (Relatedly, the jagged SDSC curve in `size_priority_table.png` is
largely sampling noise: SDSC spans dozens of distinct job sizes with few observations
each, versus 6 on LANL and 8 synthetic.)
What is not in question on either machine is the degeneracy itself, and on LANL the
ML scheduler also fails to beat plain FCFS (p = 0.48).

## Phase D: the non-degeneracy sweep — the converse condition, demonstrated

The paper *stated* a converse condition — a feature set can rank finer than the size
partition only if it carries a per-job attribute that is **not** a function of requested
size given the state — but never demonstrated it. This sweep does
(`04_scheduler/non_degeneracy_sweep.py`, pipeline step 12,
`05_results/degeneracy/non_degeneracy_sweep.csv`, 14 rows = 7 feature sets × 2 traces).

**It is a parallel experiment, and it agrees with the published one.** The sweep's
`baseline` arm reproduces the published diagnostic field for field: SDSC 11,843 ranking
instants, τ 0.751883, 14.413578% all-tied; LANL 29,943 instants, τ 0.620662, 20.729386%
all-tied. Its `mean_wait_min` column also reproduces the published trace-benchmark means
(SDSC 145.0 / LANL 37.2, and the `+est_runtime` arm reproduces `PROACTIVE_EST` at 125.0 /
37.0). Because the control agrees, the other 12 rows are readable against it.

Five per-job attributes were added, one at a time and then all together: the user's
runtime estimate (SWF requested time), causal per-user mean wait, causal per-user mean
runtime, queue identity, and user identity. **Every one breaks the degeneracy, on both
traces.**

on the walltime the user already typed into the submit script.

**The deliverable sentence, supported in both halves:** adding a per-job feature that is
not a function of requested size given the cluster state **breaks the degeneracy**, but
does **not** by itself make the scheduler better than a simple runtime heuristic.
Non-degeneracy is **necessary, not sufficient**.

### Causality note on the per-user history features

A per-user history computed over the full trace with a plain `groupby` would leak the
future and **manufacture a fake non-degeneracy** — the "history" feature would carry the
answer. The implementation absorbs a job into its user's running means only once that job
has **completed** (`submit + wait + runtime <= t`), not merely once it has been
submitted, because a job's wait is unobservable before it starts. A user with no
completed prior job gets `NaN` (cold start). Three tests in `tests/test_non_degeneracy.py`
pin this down and go red under a full-trace `groupby`:
`test_user_history_does_not_leak_a_later_extreme_wait`,
`test_user_history_excludes_jobs_submitted_earlier_but_not_yet_completed`, and
`test_history_is_prefix_stable_under_appended_future`.

## Phase D: four adversarial attacks on the degeneracy claim

Four deliberate attempts to break the claim, under the full 20-window protocol on both
traces (`04_scheduler/robustness_attacks.py`, pipeline step 13,
`05_results/degeneracy/robustness_attacks.csv`, 14 rows). The `A0` control row
reproduces the published diagnostic exactly, so each attack is read against a
like-for-like baseline.

| Attack | Trace | Instants | Violations | τ vs size | All-tied | Distinct levels | Order = size order | Verdict |
|---|---|---|---|---|---|---|---|---|
| A0 baseline: published pointwise regressor | SDSC | 11,843 | 0 | 0.7519 | 14.41% | 3.088 | 71.53% | control |
| A1 XGBRanker `rank:pairwise` | SDSC | 11,852 | **0** | 0.8153 | 14.47% | 3.093 | 74.43% | NOT BROKEN |
| A1 XGBRanker `rank:ndcg` | SDSC | 11,877 | **0** | 0.6953 | 14.29% | 3.100 | 67.46% | NOT BROKEN |
| A2 monotone transform: log1p | SDSC | 11,843 | **0** | 0.7519 | 14.41% | 3.088 | 71.53% | NOT BROKEN |
| A2 monotone transform: sigmoid | SDSC | 11,843 | **0** | 0.7519 | 14.41% | 3.088 | 71.53% | NOT BROKEN |
| A3 history window: state 5 ticks ago | SDSC | 11,883 | **0** | 0.8178 | 13.67% | 3.094 | 75.17% | NOT BROKEN |
| **A4 score computed at enqueue and cached** | SDSC | 12,029 | **20,482** | 0.3413 | 0.058% | 8.809 | 15.75% | **BROKEN** |
| A0 baseline: published pointwise regressor | LANL | 29,943 | 0 | 0.6207 | 20.73% | 2.277 | 77.63% | control |
| A1 XGBRanker `rank:pairwise` | LANL | 30,260 | **0** | 0.5980 | 20.68% | 2.289 | 72.54% | NOT BROKEN |
| A1 XGBRanker `rank:ndcg` | LANL | 30,130 | **0** | 0.4702 | 20.44% | 2.308 | 68.61% | NOT BROKEN |
| A2 monotone transform: log1p | LANL | 29,943 | **0** | 0.6207 | 20.73% | 2.277 | 77.63% | NOT BROKEN |
| A2 monotone transform: sigmoid | LANL | 29,943 | **0** | 0.6207 | 20.73% | 2.277 | 77.63% | NOT BROKEN |
| A3 history window: state 5 ticks ago | LANL | 29,587 | **0** | 0.6137 | 20.58% | 2.269 | 77.48% | NOT BROKEN |
| **A4 score computed at enqueue and cached** | LANL | 31,524 | **37,741** | 0.4967 | 0.209% | 8.017 | 20.27% | **BROKEN** |

- **A1 — a different learning objective.** Degeneracy is a property of the *inputs*, not
  of the loss: if every per-job feature is a function of size given the state, so is any
  function of them. A pairwise and an ndcg learning-to-rank model over the identical 8
  features produce **not one counterexample** on either trace. τ moves over 0.470–0.815 —
  a different objective learns a *different* size→priority table — but the partition it
  can express is the same one.
- **A2 — monotone transforms of the published score.** log1p and sigmoid: 0 violations,
  and the rows are numerically **identical to the baseline in every order-derived
  column**. This attack fails by construction; a non-zero count here would have meant the
  instrumentation was broken, not the claim.
- **A3 — a history window of 5 lagged cluster states.** 0 violations on both traces. A
  lagged cluster state is still **shared** by every co-queued job at the dispatch instant,
  so the lag block lands in the same "identical for every queued job" bucket as the
  contemporaneous one.
- **A4 — score computed at enqueue time and cached. This one succeeds.** 20,482
  violations on SDSC and 37,741 on LANL; the all-tied fraction collapses from 14.4%/20.7%
  to **0.058%/0.209%**, distinct priority levels rise to 8.81/8.02, and the induced order
  matches the size order in only 15.8%/20.3% of instants.

**The scope limitation this forces the paper to state.** The degeneracy claim holds for a
score computed **at the dispatch instant**. A pipeline that scores a job on arrival and
caches the result scores different jobs against *different* cluster states, so the
shared-state premise fails by construction and that variant is measurably non-degenerate.
Claiming the degeneracy for "wait-time-model schedulers" in general would be wrong.

**But it does not rescue the approach.** Staleness is a cost as well as a source of
variation, and the same 20-window protocol measures it
(`05_results/degeneracy/robustness_attack_utility.csv`, waits in seconds):

| Trace | Policy | Jobs | Mean wait (s) | Median wait (s) | Mean bounded slowdown | vs PROACTIVE |
|---|---|---|---|---|---|---|
| LANL | PROACTIVE | 18,505 | 2229.3 | 0.0 | 6.13 | — |
| LANL | PROACTIVE_ENQUEUE_CACHED | 18,505 | 2491.1 | 0.0 | 7.78 | **+11.74% worse** |
| LANL | SJF_USEREST | 18,505 | **1889.2** | 0.0 | **4.51** | −15.26% |
| SDSC | PROACTIVE | 6,170 | 8701.7 | 76.0 | 18.49 | — |
| SDSC | PROACTIVE_ENQUEUE_CACHED | 6,170 | 8559.0 | 105.4 | 21.56 | −1.64% (mean only) |
| SDSC | SJF_USEREST | 6,170 | **6946.3** | 98.1 | **14.70** | −20.17% |

On LANL the non-degenerate variant is 11.7% worse on mean wait and 27% worse on bounded
slowdown. On SDSC it is 1.6% better **on the mean only** — its median wait rises from
76.0 s to 105.4 s and its bounded slowdown from 18.49 to 21.56, both worse. On both
machines the ML-free `SJF_USEREST` one-liner beats it. The one non-degenerate variant
these attacks found is a **different and largely worse policy**. The negative result is
**narrowed in scope, not weakened in force**.

**External validity, unchanged.** Both halves of Phase D run on the same two 1990s traces
(LANL CM-5 1994, SDSC SP2 1998). No modern GPU-cluster trace was added;
`reports/d3_modern_trace_gap.md` records why, the specific obstacle per candidate trace,
and the minimum fields a candidate must supply (including at least one genuine per-job
attribute — SWF field 9, 12 or 15 — for the sweep above to be runnable on it). No claim
here should be read as external validity beyond these two machines.

## v3.4: trace-driven re-evaluation on real workloads

20 paired 7-day windows per trace (3-day warm-up, not measured), offered load ≈0.70,
event-driven and second-exact, using **the real user runtime estimates the SWF traces
contain** rather than a simulated estimate model. Mean wait in minutes / mean bounded
slowdown (`05_results/trace_schedulers/`):

|---|---|---|---|---|
| SRPT (oracle, preemptive) | 60.1 | 1.1 | 14.6 | 1.1 |
| SJF (oracle) | 110.8 | 13.2 | 23.0 | 2.8 |
| SJF (**real** user estimates) | 115.8 | 14.7 | 31.5 | 4.5 |
| HRRN (real estimates) | 126.3 | 16.8 | 29.5 | 5.0 |
| Proactive **+ estimate feature** | 125.0 | 14.7 | 37.0 | 5.8 |
| Smallest-first (no ML) | 145.0 | 19.0 | 42.5 | 6.6 |
| **Proactive (XGBoost)** | 145.0 | 18.5 | 37.2 | 6.1 |
| FCFS + first-fit | 174.6 | 34.7 | 38.8 | 8.2 |
| EASY backfill (oracle) | 183.7 | 35.7 | 46.0 | 8.5 |
| EASY backfill (real estimates) | 195.1 | 42.5 | 80.2 | 20.6 |
| Conservative backfill | 207.5 | 40.5 | 113.6 | 28.4 |
| Strict FIFO | 755.1 | 281.5 | 205.7 | 71.4 |

- **The synthetic gain does not replicate.** Proactive beats FCFS by 20.4% on SDSC
  (p=0.042, Holm 0.084) but by only 4.5% on LANL, **not distinguishable from zero
  (p=0.48)**. An advantage over doing nothing that is machine-dependent and
  insignificant on one of two real machines is not established.
- **Any runtime signal dominates.** SJF on the estimate the user actually typed beats
  Proactive by 20.2% on SDSC (Holm p=0.009) and 15.3% on LANL.
- **ML adds nothing on top of the estimate.** `PROACTIVE_EST` — the same model
  retrained *with* the user estimate as a feature, so it can in principle learn
  everything SJF exploits plus the cluster state — still loses to plain SJF on both
  machines (+7.9% SDSC, +17.5% LANL). The pipeline's ceiling is the sort it is
  trying to learn.
- Bounded slowdown separates the policies far more sharply than mean wait and in the
  same direction; mean wait alone hides the effect on short jobs.

| Mean est/runtime | 61.4× | 23.8× | 3.00× |
| Within 2× | 24.0% | 41.7% | — |
| **Under-estimates** | 0.1% | **36.3%** | **0%** |

The two machines occupy opposite regimes and neither is the f-model, which by
construction (`est = runtime · U(1,C)`) **cannot produce an under-estimate at all**.
This is not cosmetic: v3.3 concluded from the f-model that EASY is "nearly
insensitive to estimate quality" (18.9–19.8 ts across perfect/f-model/modal). On the
traces, real estimate error costs EASY **+6.2% mean wait on SDSC but +74% on LANL**
(paired t p = 0.025 raw, 0.23 after Holm; the Wilcoxon signed-rank test on the same 20 windows gives Holm p = 2.1e-05 — the effect is real but the heavy tail is what carries it, so the rank test survives correction and the t-test does not) versus perfect estimates. Under-estimates break the mechanism the
reservation depends on — a job that claims it finishes before the shadow time and
does not *does* delay the head. An evaluation using over-estimate noise only cannot
observe this failure mode; the f-model should not be the sole estimate-error model
in backfill studies.

## v3.4: simulator fidelity (limitation)

Against the recorded waits in the traces, simulated FCFS is close on LANL (38.8 vs
33.2 min mean — the simulator is slightly *pessimistic*) but far more permissive on
SDSC (174.6 vs 630.9 min mean, against a recorded per-window median averaging 19.3 min — a mean of the 20 window medians, not a pooled median, which is 7.2 min). SDSC's
recorded mean is dominated by an extreme tail our capacity-only model cannot
reproduce, because SWF records no per-node placement or site policy (partitions,
per-user limits, administrative holds). SDSC results should be read as "a correctly
loaded 128-processor machine driven by the real arrival/size/runtime/estimate
distributions", not as a replay of SDSC's actual queue. **The degeneracy result does
not depend on this** — it is a property of the feature vector and holds in all three
substrates. See `trace_fidelity.csv`.

## v3.6: the evaluation split, and the headline accuracy it changes

The published **R² 0.837 / MAE 4.69** came from `train_test_split(test_size=0.2,
random_state=42)` over 2,200 rows — but those rows are 20 simulation runs of 110 jobs, and
every row of one run shares that run's cluster trajectory, so a random *row* split puts
near-duplicate instants on both sides of the partition. Re-evaluated under four protocols
(`05_results/models/evaluation_splits.csv`, `03_models/evaluate_splits.py`):

| Split | Folds | Train/test rows | R² | MAE (ts) |
|---|---|---|---|---|
| Random rows (published protocol) | 1 | 1760 / 440 | 0.836840 | 4.6935 |
| **Run-wise `GroupKFold` on `run_id` (headline)** | 5 | 1760 / 440 | **0.810910 ± 0.020672** | **4.8970 ± 0.4492** |
| Leave-one-run-out | 20 | 2090 / 110 | 0.793486 ± 0.054176 | 4.8207 ± 1.0156 |
| Chronological (deployment order) | 1 | 1753 / 447 | 0.725147 | 7.2403 |

**The headline model accuracy is now the run-wise number, R² 0.81 (0.810910 ± 0.020672),
MAE 4.90 ts.** It is **lower than the 0.837 previously reported here**, and it is lower for
a reason: it is the only split that answers whether the model works on a cluster trajectory
it has not seen. Five folds were used precisely so the training set stays at 1,760 rows —
the same size as the random split — so the gap cannot be blamed on less training data.
Leave-one-run-out is a sensitivity check on the fold count, not the headline: its per-fold
R² spans 0.6899 to 0.8744, which is why a single grouped hold-out would have been
unquotable.

**Any deployment claim must quote the chronological MAE of 7.24 ts, not 4.69.** Training on
each run's earlier arrivals and testing on its later ones is what a deployed model actually
faces, and it costs 54% more error than this repository used to advertise.

For scale, the constant-predictor baselines in the same file: mean-constant R² −0.006005
(MAE 13.2867) on the random split, −0.019958 on the run-wise folds (median-constant
−0.088624), and −0.702853 (MAE 19.2303) on the chronological split. Against the run-wise
constant baseline the model still cuts MAE by about 64%, so it is a real but ordinary
regressor, not a dressed-up mean — the reader needs both halves of that.

**None of this touches the central contribution.** Ranking degeneracy is a statement about
the functional *form* of the score — at a fixed dispatch instant every queued job observes
the same cluster state, so the score is a function of requested size alone — and it holds
whatever the accuracy is. A more accurate model produces the same one-line sort.

## High-level findings
- Model quality: **R² 0.811 ± 0.021, MAE 4.90 ± 0.45 ts** under run-wise `GroupKFold` on `run_id` (`05_results/models/evaluation_splits.csv`, `03_models/evaluate_splits.py`). This is **lower than the "R² ≈ 0.84, MAE ≈ 4.69 ts on a proper 20% holdout" previously quoted here**, which came from a random *row* split that leaks a run's own trajectory across the partition; the row-level 5-fold CV figure quoted alongside it resamples rows rather than runs, carries the same leakage, and is withdrawn as a generalisation estimate. In deployment order the model is weaker again — chronological MAE **7.24 ts**. See the split section above. In-sample (full-data) evaluations overstate generalisation and must not be quoted as model quality.
- Proactive scheduling: **7.9% mean wait-time reduction** vs FIFO (40-run seeded paired benchmark, paired t-test p = 2.0e-06, Wilcoxon p = 2.7e-06, **Student-t** 95% CI on improvement [4.9%, 10.9%] from `04_scheduler/benchmark_statistical.py`), at **identical GPU utilisation** (≈64% — `baseline_util` equals `proactive_util` in 40 of 40 runs, mean 0.641177, identical to six decimal places). That interval was previously mislabelled "bootstrap"; it is a `stats.t.ppf` interval. The repository's one true percentile bootstrap, `phases_22_30/phase_22_stats/stats_bootstrap.py`, gives [4.9%, 10.7%] over the same 40 runs.
- Trade-off: proactive reordering **worsens tail latency** (mean max-wait ~58 → ~123 ts) and **per-job fairness** (Gini 0.53 → 0.79). The anti-starvation variant recovers part of the equity loss (Gini 0.69, max wait ~88 ts) at a small mean-wait/SLA cost. The mean-wait gain is not free.
- **Real-trace validation (v3.2)** — two genuine Parallel Workloads Archive traces (`.swf.gz` committed): zero-shot transfer of the synthetic model is **R² ≈ 0 on both** (SDSC SP2 0.072, LANL CM-5 −0.001, even with best-case affine calibration). **Retrained on the trace itself** (chronological 80/20 split, log-wait target): **SDSC SP2 R²(log) = 0.494** / MAE 622 min (vs −0.694 / 684 min median baseline) — cluster-state features explain ~half the log-wait variance on a real batch supercomputer; LANL CM-5 only 0.101 (train-split median wait 0.05 min ≈ 3 s per the artefact's own note; largely interactive — honest partial negative). Signal is machine-dependent; retrain-per-deployment is now evidence-backed. Pipeline: `02_data/build_real_trace_datasets.py` → `02_data/real_trace_validation.py`.
- OOD robustness (Phase 23, 72 shifted scenarios, real model, real simulations): mean R² ≈ −0.31 (range −2.3 to +0.85); scheduling improvement swings −10% to +53% with ≈32% mean failure rate. Retraining per deployment regime plus a FIFO fallback is required.
- **The OOD failure taxonomy was a constant, and is now a ranking (v3.6).** Any sentence in an earlier draft describing "the OOD failure taxonomy" was describing a column that said the same thing 72 times: every one of the 72 scenarios in `phases_22_30/phase_23_sensitivity/ood_failure_modes.csv` carried the label `DISTRIBUTION_MISMATCH`, zero entropy. The cause is identified rather than guessed at — the classifier tested `mape >= 35.0` ahead of most branches and the *minimum* MAPE over the 72 scenarios is **54.01**, so that gate fired 72 times out of 72 and seven of the eight categories were unreachable dead code; `risk_level` was 65 MEDIUM / 7 HIGH / 0 LOW. The column is rebuilt (now 18 columns over the same 72 rows) as a continuous severity score standardised across the grid, four data-derived quantile bands of 18 scenarios each, and a dominant-axis label: `failure_mode` now spans five values (COMPLETION_DOMINATED 22, POLICY_DOMINATED 21, FIT_DOMINATED 14, NO_DOMINANT_AXIS 8, CALIBRATION_DOMINATED 7) and `risk_level` three (MEDIUM 37, HIGH 24, LOW 11). **Severity is standardised *within* this grid**, so `LOW_RISK` means "least severe among 72 shifted regimes" and never "safe" — none of these regimes is good, and the mean R² across them is negative (−0.31). The simulation, the scenarios and the seeds are unchanged; only the classification of the results is.
- Model comparison (Table 1): LightGBM 4.61/0.848 ≥ CatBoost 4.62/0.845 ≥ XGBoost 4.69/0.837 ≈ RF ≈ MLP; linear regression trails (6.32/0.761). Gradient-boosted trees are the right model family; the specific library is a wash. All seven rows are scored on the random row split, so they remain comparable *to each other* while each is optimistic in the same direction (see the split section).
- **Phase 12 ablation, now with intervals and a collinearity check (v3.6)**: each ablation is re-fit over 20 leave-one-run-out folds on `run_id`, the drop paired within fold, with a Student-t 95% interval over the 20 paired differences (`05_results/models/ablation_study_results.csv` — byte-identical to `05_results/ablation_study_results.csv`, one artefact under two names — via `03_models/ablation_study.py`). The honest baseline falls with the protocol: R² 0.836840 on the single fixed row split → **0.793486 [0.767472, 0.819500]** leave-one-run-out. **Only three of the twelve drops are distinguishable from zero**: `job_gpu` 0.2051 [0.1565, 0.2538], `queue_length` 0.0217 [0.0081, 0.0353], `queue_pressure` 0.0158 [0.0051, 0.0264]. The other nine intervals span zero — which means the drop is *not distinguishable from zero at this sample size*, **not** that the feature adds nothing; accepting a null from a failure to reject it is exactly the error this repository criticises elsewhere, and is why it uses TOST for equivalence rather than a large p-value. The earlier single-split ordering (`job_gpu` 0.201, then `queue_pressure` 0.027 and `queue_length` 0.021) is superseded: under the paired folds the second and third places swap, and their intervals overlap. **Two of the twelve features are also the same variable twice** (`05_results/models/feature_collinearity.csv`): `total_free` and `avg_free_per_node` correlate at 1.000000 with **infinite VIF** — in the synthetic generator one is the other divided by a constant node count — and `fragmentation`/`variance_free` correlate at 0.950720 (VIF 66.8 and 34.1). A single-feature ablation cannot say anything about either member of such a pair: dropping one leaves the information intact in the other, so a near-zero drop there is arithmetic, not evidence. `queue_pressure` surviving as one of only three real contributors is *consistent* with the degeneracy result rather than in tension with it — v3.5 established that `queue_pressure` is itself a deterministic function of requested size given the cluster state.
- Phase 13/27 fairness: quantified above; SLA compliance FIFO 0.933 vs Proactive 0.945 vs anti-starvation 0.863.
- Phase 14/24 benchmark, now **14 schedulers** (v3.4 adds SMALLEST; 20 paired runs, out-of-training seeds, unified wait = turnaround − runtime, canonical two-condition EASY): mean wait **SJF-oracle 12.34 < SJF-EST 13.32 < SRPT 14.02 < HRRN 15.55 < Proactive 15.95 < NN 16.07 = SMALLEST 16.07 < static priority 16.53 < FCFS/first-fit 17.22 < Hybrid-BF 19.20 ≈ EASY-EST 19.23 ≈ EASY 19.25 < Conservative-BF 21.84 < strict FIFO 26.17 ts**. All gaps vs Proactive are Holm-significant except HRRN (−2.5%, t p=0.17 Holm), `STATIC_PRIORITY`, and **NN/SMALLEST (+0.8%, Holm n.s., TOST-equivalent; NN and SMALLEST tie with each other exactly** — see the degeneracy section). Labels: "FCFS/first-fit" is the historical 'FIFO' key (any fitting job starts per tick); strict FIFO blocks on the queue head. The `STATIC_PRIORITY` key (mean wait unchanged at 16.53) was previously labelled "Priority + aging" — **that label was false and is retracted**: the key expands to `(priority_score + 0.03·arrival_time) − 0.03·current_time`, and the `current_time` term is a common additive shift at any dispatch instant, so it cancels pairwise, the induced order is time-invariant, and a waiting job can never overtake. Any claim that its aging prevents starvation is withdrawn. HRRN is the repository's genuinely aging baseline.
- **The guide-requested baseline landscape (v3.3)** answers "does the ML model beat classical logic?" honestly: **any runtime signal beats it on mean wait** — even SJF on rank-destroying modal estimates (everyone writes 10 or 20 ts) gets 14.06 vs Proactive's 15.95, and the estimate-quality sweep (f-model C=1→10, `05_results/schedulers/estimate_sensitivity.csv`) only degrades SJF-EST from 12.34 to 13.49. But runtime-ordered policies pay in tails/equity (SJF max 146 ts, Gini 0.79; SRPT max 151, Gini 0.81, 41.5 preemptions/run at 1-tick checkpoint cost), where HRRN (aging built into the ratio) is the strongest classical all-rounder: mean 15.55, max 65, Gini 0.54. **Proactive's niche is the zero-runtime-information regime**: −7.4% mean wait vs FCFS/first-fit (Holm p=4.0e-04) using only observable cluster/queue state, no estimates. Per-run rows + Holm-adjusted pairwise tests (t + Wilcoxon): `multi_scheduler_runs.csv`, `multi_scheduler_significance.csv`.
- **Backfill, canonically (v3.3)**: the v3.2 EASY implementation omitted Mu'alem & Feitelson's second backfill condition (candidates fitting in the shadow-time surplus may run past it) and overstated the reservation price at ~45%; the canonical rule costs **+11.8% mean wait vs FCFS/first-fit** (19.25 vs 17.22) while beating strict FIFO by 26% — and is nearly insensitive to estimate quality (18.9–19.8 across perfect/f-model/modal estimates; mild over-estimation even helps, reproducing the known paradox). Conservative backfill (reservation for every queued job) trades +13% further mean wait for the study's best tail (max 50 ts) short of strict FIFO's Gini. The predicted-wait backfill hybrid lands at 19.20 against plain EASY's 19.25 — a 0.05 ts gap on a ~19 ts mean. **The earlier "(n.s.)" on that pair is withdrawn: no paired test between `PROACTIVE_BF` and `BACKFILL` exists anywhere in the repository** (`multi_scheduler_significance.csv` uses only PROACTIVE and FIFO as references). The hybrid buys nothing visible, but that is an observation about two means, not a tested null.
- **Bounded-fairness wait-budget (v3.2)**: sweeping a hard escalation budget B traces a smooth Pareto frontier — B=60 keeps +7.4% mean-wait gain (of +13.1% unbounded) while capping max wait at 81 ts (vs 138) and Gini at 0.68; B≤30 is slightly worse than FIFO (escalation churn). `05_results/fairness/budget_sweep.csv`.
- **Uncertainty-aware scheduling (v3.2, honest negative)**: quantile XGBoost (q10/50/90; holdout q50 MAE 4.61) has under-dispersed intervals (68% coverage vs 80% nominal); UCB and spread-guarded variants match the point model everywhere and fail to detect the one regime where reordering hurts (0.5× arrivals / 4 nodes: −2…−5% vs FIFO across all three variants, guard fired on 0.5% of ticks). Rolling-MAE drift triggering remains the deployment mechanism. `05_results/uncertainty/`.
- **Censoring / selection audit (v3.6, and it runs the other way)**: under load a policy's published mean wait is computed over the jobs that actually *started*, and two policies need not start the same set, so `04_scheduler/censoring_analysis.py` re-runs the same simulations and recomputes every improvement on the common set of jobs started under *both* policies (`05_results/uncertainty/censoring_analysis.csv`). Four of the five scenarios start every job under every policy: **24 of the 30 pair-rows have a selection gap of exactly 0.0 pp** and there is nothing to correct. All the censoring sits in `arr2.0_nodes4` — and there **all six non-zero gaps are negative** (−0.38 to −3.25 pp), meaning the common-set improvement is *larger* than the published one: the published statistic **understated** the learned policies by up to 3.3 pp. Nothing disappears on the common set. The concern is therefore **not refuted but measured and signed**: the selection effect is real, is confined to one of five scenarios, and runs in the direction that penalised the learned policies. What the common set does *not* do is adjudicate everything — for FIFO vs PROACTIVE in that scenario it compares only the ~91.9 jobs started under both, against 21.8 started only under FIFO and 39.4 only under PROACTIVE (means over 10 runs). Those ~61 exchanged jobs are a two-way exchange, not a one-way rescue, and they are described rather than adjudicated.
- Phase 15 SHAP, **now computed on held-out data (v3.6)**: the explanations used to cover 400 rows sampled from the *full* dataset with the full dataset as background — roughly 320 of those rows were inside the model fit. They now come only from the 440-row held-out test split, with a background drawn from that split: `rows_from_training = 0`, verified by a sha256 fingerprint of the actual explained row indices rather than by self-report (`05_results/shap/shap_provenance.csv` and `shap_explained_rows.csv`, from `03_models/explainability_shap.py`). **The ordering is essentially unchanged, and that is the point**: `job_gpu` still dominates at mean |SHAP| 7.3393 — 35.4% of all attribution mass and 76.2% of the mass carried by the four job-dependent features — and the only rank movement is a 7/8 swap between `running_jobs` and `variance_free`, which differed by 0.0003, i.e. noise. The degeneracy story is one the corrected provenance confirms, not one that depended on the leak. Global summary, 12 dependence plots, and 3 force plots regenerate cleanly (`05_results/shap/`).
- Phase 16–19: scaling (advantage 14.5% on small contended clusters → 0% when capacity removes queueing), online learning (drifted-stream MAE 6.98 → 6.88 with incremental updates), and concept drift detection (rolling-MAE triggers).
- **The ROI study is withdrawn and deleted (v3.6).** It converted a wait-time percentage into GPU-hours saved and priced them; every dollar figure and percentage return this file used to carry — the ~$80k/yr saving and the ~90% first-year return — is retracted, because **the quantity being monetised was measured at zero**. In the 40-run seeded benchmark `baseline_util` equals `proactive_util` in **40 of 40 runs** (mean 0.641177, identical to six decimal places), with the same 110 jobs completing under both policies (`05_results/benchmark_statistical_results.csv`): the cluster performs the same compute either way, because reordering a queue changes *when* jobs start, not how many GPU-hours they consume. This is a category error rather than an uncertain assumption — widening the error bars on a number whose true value is zero still reports a saving — so `05_results/roi_analysis.py`, `05_results/roi/`, the pipeline step and the dashboard panel are deleted rather than re-estimated. **The wait-time reduction itself (7.9% vs FIFO) is untouched and remains a real measured result**; what is withdrawn is the claim that it converts into money.
- Phase 22 statistics: the headline improvement carries a genuine percentile-bootstrap CI — **[4.9%, 10.7%]** (`phases_22_30/phase_22_stats/stats_bootstrap.py`) — alongside BH-corrected p-values; degenerate comparisons (zero-variance utilisation/completions) are explicitly reported as "n/a (zero variance)" instead of fake significance. This is the *only* bootstrap in the repository: the blanket claim that "all headline claims carry bootstrap CIs" is withdrawn, because the intervals produced by `04_scheduler/benchmark_statistical.py` are Student-t.
- Phase 26 stress test: at 32–256 GPUs under saturation, utilisation stays **above 99.69%** (the minimum, at 256 GPUs, is 99.694% — the previously quoted ">99.7%" bound is false as written) and scheduling overhead stays **<5% of throughput** (peak 1.55%). Inference latency is a wall-clock measurement and is machine-dependent: the committed run records **10.24–15.49 ms** per decision across the four scales, non-monotone in cluster size, and on a repeat run of this repository the timing columns moved by up to 84% while every non-timing column stayed bit-identical. The previously quoted "10–48 ms" is not the range in the committed artefact and is withdrawn.
- **Scaling verdict withdrawn (v3.6).** Earlier versions fitted a scaling law to the latency points committed at that time (48.05, 9.60, 28.40, 19.49 ms — not the four above, because this column is wall-clock and moves between runs, which is itself the objection) and reported "O(1) / latency is CONSTANT", "excellent scalability", and projections to 512 / 1024 / 4096 GPUs. **All of that is retracted.** The fitted exponent was −0.234 over four non-monotone wall-clock points, and the classifier's test was one-sided, so a *negative* exponent was labelled "constant" by fall-through. Four noisy, non-monotone points cannot identify a complexity class, and no projection past the largest measured cluster is defensible. `phases_22_30/phase_26_scaling/scaling_law_fit.txt` is accordingly renamed `scaling_measurements.txt` and reports no complexity class. What survives is the overhead and utilisation bound above.

## Publication-ready package
The repository includes a seeded one-command reproducibility script, container setup,
structured result outputs, dashboard support, a deployment guide (`DEPLOYMENT.md`),
and full project documentation (`docs/explanation.html`). The manuscript
(`phases_22_30/phase_28_manuscript/manuscript.tex`) was **reframed in v3.4** from
"we propose an ML scheduler that beats FIFO" to what the evidence supports: an
evaluation study and a negative result, titled *"Ranking Degeneracy: A Learned
Wait-Time Model Schedules No Better Than Sorting by Requested Size"*. It reports the
degeneracy proof and measurement, the TOST equivalence results, the trace-driven
re-evaluation, the estimate-error finding, the fairness/tail-latency trade-off, the
backfill reservation price, the wait-budget Pareto frontier, and the sim-to-real
results — plus a stated non-degeneracy condition for feature sets and two
methodological recommendations (report the ML-free control the feature set implies;
use equivalence tests, not failed difference tests).
